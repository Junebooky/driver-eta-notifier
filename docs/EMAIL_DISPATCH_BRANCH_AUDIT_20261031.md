분기 때문에 안전하다고 무조건 단정할 수 없다. 특히 커밋 포함 여부와 기능 포함 여부는 다르다. 전체 PR을 main에 개별 병합하기 전에 중복 파일/옛 마이그레이션을 별도 검토해야 한다.

## 기존 구현에서 확인한 단절

- Gemini 서비스는 이미 여러 날짜의 waypoints를 추출하고 Step1/Step2도 날짜를 표시한다.
- 이메일 최종 배차는 첫 기사·첫 차량·주 출발/도착지만 저장했다. 날짜별 끝 시간, 모든 차량 슬롯, 중간 경로가 저장 흐름에서 누락됐다.
- 기사 확인 API, 버전 변경 시 재확인, HQ 확인 표시는 이미 있다. 관리자 대신 확인 및 이름 기반 확인 권한을 제거하고 실제 지정 UUID를 요구하도록 보완했다.

## 이번 연결

- 기존 추출 결과를 순서대로 날짜별 묶음으로 변환한다. 날짜/출발·도착/시작 시간 부족은 추정하지 않고 보완을 요구한다. 날짜를 건너뛰며 가짜 이동 구간을 만들지 않는다.
- 기존 TMAP 검색 입력으로 각 경유지를 확인하고 실제 종료 시간을 입력한다. 각 차량 슬롯에서 기사와 실제 번호판을 별도로 선택한다.
- 모든 날짜×차량을 기존 원자적 배차 API에 한 번에 보낸다. 중간 경유지도 기존 schedule_meta에 보존하고 기사 앱의 adminWaypoints로 전달한다. 경로 변경도 기존 버전 재확인 조건에 포함한다.
- 대표 지정 요청은 같은 API의 미배정 예약으로 저장한다. HQ 계정의 콕핏에 요청 목록 링크/건수를 표시하며 모바일·PC에서 같은 예약을 연다. 서버 요청을 저장한 것이며 외부 푸시/SMS 발송을 보장하지 않는다.
- 저장한 이메일 요청은 새로 만들지 않고 기존 예약 목록에서 배정한다. 출처 이메일·날짜·차량 슬롯 고유 인덱스 제안으로 서로 다른 운영자의 중복 생성도 차단한다.
- 완료 화면의 로컬 수락/거절 스마트폰 모형을 제거했다. 저장된 모든 날짜의 서버 확인 상태를 조회하고, 배차 버전 변경 시 재확인 대기로 표시한다. 확인 저장은 수정 시각을 대조하여 새 배차를 덮어쓰지 않는다.
- 기존 차량 관리에 8초/포커스 갱신을 추가한다. 기사 앱과 HQ의 기존 일정 조회 및 확인 표시를 재사용한다.

## 범위와 운영 조건

탑승객별 서로 다른 groupTrips는 첫 일정만 조용히 저장하지 않고 개별 예약 확인을 요구한다. 모바일에서 분리된 날짜 예약은 각각 다른 기사/차량으로 배정할 수 있다. 이메일에서 한 번에 직접 확정하는 경우 선택한 차량 슬롯을 각 날짜에 적용한다.

새 SQL은 운영에 적용하지 않았다. 기존 배차·인증·reporting 선행 조건, 개인 계정 연결과 실제 휴대폰/이메일 공급자 검수는 여전히 필요하다. 새로운 이메일 처리 엔진, 별도 모바일 서버, 별도 차량 스케줄 원장을 만들지 않았다.
