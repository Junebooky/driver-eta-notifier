# 차량 인수·반납 서버 연결

기존 차량체크의 인수/일일점검/반납·계기판 OCR·손상·주차 위치 입력을 재사용한다. 로그인·배차·운행일지·차량 관리 화면을 새로 만들지 않는다. PR #40의 P0 검수 수정 다음 단계다.

## 이번 동작

- 기존 개인 프로필 조회가 끝난 뒤 첫 실행 등록 여부를 결정해, 이미 연결된 기사에게 빈 최초 등록 화면이 뜨던 경합을 막았다. 브라우저의 이전 차량 기본값이 서버 배정 번호판을 덮어쓰지 않게 하고, 예약별 초안 복원과 서버 배정 초기화를 조정했다.
- 확인된 기사 UUID가 있는 회사 기사에게 서버 배정 일정과 전체 차량번호를 보여준다. 확정된 배정 차량을 기본 선택하며, 변경 시 회사 차량 마스터의 UUID와 전체 번호판을 사용한다. 끝 네 자리나 브라우저 프로필은 권한 근거가 아니다.
- 실제 차량번호/계기판을 확인하는 체크 후 기존 km·손상 입력으로 인수를 저장한다. 서버는 기사·조직·배차 버전·확정 상태·인수 시간 범위(픽업 6시간 전~예정 종료 6시간 후)·정비·다른 배차·기존 인수를 다시 검증한다.
- 다른 차량 선택은 사유가 필요한 ‘불일치 확인 요청’이다. 서버가 요청과 선택 차량을 보존하고 HQ/대표 대시보드·차량 관리에 8초 조회로 표시한다. 차량을 빼앗거나 기존 배차/기사 확인을 변경하지 않는다. 푸시 알림 전송을 구현한 것으로 간주하지 않는다.
- 담당자는 기존 배차 화면에서 조치한다. 확인 내용만 기록하는 버튼은 인수/차량 변경 승인이 아니다. 최신 일치 배차로 실제 인수하면 해당 기사의 이전 불일치 요청을 해결 처리한다.
- 같은 차량·기사의 열린 인수는 각각 하나만 허용한다. 기존 배차 저장과 동일한 DB 잠금 경계를 사용한다. 요청 키는 계정·API별로 구분하고 본문을 고정한다. 응답 유실/새로고침 후 ‘이전 저장 결과 재확인’으로 같은 요청을 재확인하며, 확인 전에는 변경한 본문을 저장하지 않는다.
- 인수 중인 차량/기사를 현재 상태와 요청 구간 가용성 양쪽에 반영한다. 예정 반납 시각이 지났어도 실제 반납이 없으면 미래 슬롯을 홀드한다. 실제 반납 전에는 해당 배차의 기사/차량 변경을 DB에서도 차단한다. 미래 계획은 유효한 예정 반납+회차 간격 뒤 배정을 허용하며, 실제 인수 시에는 물리적 반환 여부를 다시 검증한다.
- 반납은 인수 당시 기사·차량·인수 ID로 처리한다. 예약 취소 후에도 원래 기사가 반납할 수 있다. 반납 km는 인수 km보다 작을 수 없고 새 인수 km도 이전 반납 km보다 작을 수 없다. 계기판 교체 같은 예외를 임의 보정하지 않는다.
- 인수는 GPS 이동이나 출퇴근/운행 시작을 의미하지 않는다. 운행 완료가 물리적 반납을 대신하지 않으며, 반납이 운행 완료나 출퇴근 시각을 자동 변경하지 않는다. 정비 상태와 실제 일정은 그대로 별도 계산한다.
- 계기판 사진은 선택 사항이며 원본 JPG/PNG/WebP 3MB 이하를 기존 비공개 `cockpit-assets`에 내용 해시 경로로 보존한다. 원본 저장 실패는 성공으로 처리하지 않는다. 사진 조회는 원래 이벤트의 기사/조직 또는 HQ 권한을 검증하고 임의 경로 조회를 허용하지 않는다. OCR 결과만으로 인수를 확정하지 않는다.
- 인수 성공 시 기존 기사 화면의 선택 예약에 연결한다. 운행일지는 같은 기사·차량·예약·한국 날짜에 반납까지 완료된 기록만 명시적으로 적용한다. 수동 입력을 주기 조회로 덮어쓰지 않는다. 제출 API가 원본 인수·반납 km와 다시 대조하고 `meta.custodyId`를 저장한다. 여러 날 인수를 하루 운행 거리로 자동 합치지 않는다. 직접 수정하면 서버 원본 연결을 해제한다.
- 회사 운행일지는 오래된 localStorage 차량체크를 ‘검증된 km’로 자동 채택하지 않는다. 로컬 점검 초안은 기사·예약별로 구분하며, 독립/미연결 프로필의 로컬 차량체크와 일일점검·양식 복사 기능은 유지한다.
- 고정 차량 번호가 없는 기사도 배차 가용성 명단에 포함한다. SQL `vehicle_no <> '미배정'`가 NULL인 실제 기사까지 누락하던 문제를 수정했다.

## 적용 전제

`20261101103643_vehicle_custody_integrity.sql`은 CLI로 생성한 새 제안이며 운영에 적용하지 않았다. 선행 원자적 배차·개인 인증·보고 제안과 실제 기사 매핑/기존 예약 종료 시간 정리가 필요하다. 새 테이블 2개는 RLS를 켜고 anon/authenticated/PUBLIC 직접 권한을 회수한다. 함수는 SECURITY INVOKER, 빈 search_path, service_role 전용이다. 독립 스키마나 공용 로그인 우회를 만들지 않는다.

`supabase/checks/release_preflight.sql`에 새 테이블/RPC도 추가했다. main 병합·배포·고객 메시지 발송·운영 데이터 정리는 수행하지 않았다.

## 검증

- 새 단위 검사는 확인 필수·UUID/전체 번호판·인수 홀드/반납·동일 예약/날짜 km·회사 로컬 초안 미신뢰·접근 권한·비공개 사진 실패/중복 원본 검증을 포함한다.
- 실제 Postgres 통합 검사는 API→차량 불일치→HQ 요청/사진 접근→동시/재시도 인수→차량/기사 가용성→예약 취소 후 반납→차량 해제→원본 검증 운행일지를 연결한다. 관리자 확인 기록이 차량 변경/인수를 대신하지 않는지, 다른 기사의 반납 차단, 예정 반납 초과 후 미래 배차의 DB 거절, 마이그레이션 두 번 실행과 직접 클라이언트 테이블/RPC 거절도 검사한다.
- 로컬 브라우저/최종 CI 결과와 정확한 HEAD는 PR 설명에 기록한다. Auth·Storage·외부 공급자는 격리 fixture다. 실제 기사 계정·차고지·모바일 설치형 PWA·실물 계기판 OCR·푸시 전달을 검수했다고 주장하지 않는다.

## 남은 경계

차량이 정해지지 않은 차종 예약의 기사 직접 선점, 관리자 예외 반납/계기판 교체, 여러 예약을 가로지르는 일일 km 세분화, 회사 전체 일일 안전 점검의 서버 보존은 후속 범위다. 차량 미배정은 기존 관리자 배차를 먼저 사용한다. 차량 불일치가 저장됐다고 변경 차량 인수를 허용하지 않는다. Issue #11의 모든 설계 항목 완료로 보고하지 않는다.
