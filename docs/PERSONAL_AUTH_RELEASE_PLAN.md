# 개인 계정·프로필·저장 재시도 적용 계획

이 문서는 PR #40의 코드와 SQL 제안을 실제 운영에 연결하기 위한 절차다. 이 작업에서 운영 DB 변경, 계정 생성, 초대 발송, 배포 또는 main 병합은 수행하지 않았다. 기존 33개 기사 행을 합치거나 지우지 않는다.

## 변경과 전제

- 운영 로그인은 개인 Supabase Auth 이메일·비밀번호를 사용한다. 등록된 TOTP 요인이 있으면 인증 앱 번호를 요구한다. 공용 기사 PIN, HQ 비밀키 및 기존 `cockpit_s1` 토큰은 운영에서 거절한다.
- 권한은 Auth 서버가 반환한 `app_metadata.org`, `cockpit_role`, `driver_id`로 결정한다. `user_metadata`, 브라우저 차량 선택 및 요청의 role/name은 권한 근거가 아니다.
- 각 API가 `auth.sessions`의 실제 세션과 로컬 철회 목록을 확인한다. [Supabase 세션 문서](https://supabase.com/docs/guides/auth/sessions)는 JWT의 `session_id`를 실제 세션 행과 대조하도록 안내한다. JWT 만료만 기다리는 로그아웃을 피하기 위해 철회 행을 먼저 기록한다.
- `20261031024614_cockpit_personal_auth.sql`은 rate-limit/철회 테이블과 service-role 전용 함수를 추가하고 기사 테이블의 직접 클라이언트 접근을 막는다. 제안의 함수나 Auth 설정이 없으면 인증은 실패로 처리한다.
- 프로필 수정은 기존 `drivers.id`를 잠그고 수정한다. 차량 배정은 예약의 `driver_id`/`vehicle_id` 관계로 처리한다. 차량 번호를 바꿔 프로필·면허증·운행 기록의 소유자를 변경하지 않는다.
- 배차 HTTP 생성·수정 요청은 `Idempotency-Key`를 요구한다. 키를 조직·사용자·API 경로별로 묶고 본문 지문을 대조한다. 클라이언트는 실패가 불확실한 요청을 같은 본문으로 재확인한다. 새 내용으로 덮어쓰지 않는다. 모든 외부 호출자도 이 헤더를 제공해야 한다.

## 격리 검증 → 운영 적용 순서

1. 병합 순서는 기존 스택 #38 → #39 → #40이다. 각 PR의 변경과 CI를 확인하고, #40을 main으로 옮길 때 베이스 변경에 따른 차이를 다시 검토한다. 기존 브랜치를 강제로 덮어쓰지 않는다.
2. 소유자가 승인한 백업/복구 지점을 확보한다. 현재 schema/컬럼/FK/RLS/role grant와 Auth 버전을 읽기 전용으로 기록한다. 특히 `auth.sessions(id,user_id,not_after)`, `cockpit.drivers`의 프로필 컬럼 존재를 확인한다. 과거 SQL은 `public`/`cockpit`과 타임스탬프가 섞여 있으므로 폴더 전체를 운영에서 재생하지 않는다.
3. 별도 Supabase 스테이징에서 실제 스키마 차이를 검토한다. 먼저 `20261030_atomic_dispatch_and_fleet_schema.sql`, 다음 개인 인증 제안을 적용한다. 운행일지·경비·자료 기능은 별도 reporting/asset 제안 및 차량 마스터가 선행되어야 한다. 순서를 바꿔도 된다고 추정하지 않는다.
4. 스테이징의 Auth 사용자별로 관리자가 `app_metadata`를 설정한다. HQ: `org=vip_limousine_korea`, `cockpit_role=hq_admin`. 기사: 같은 org, `cockpit_role=driver`, 확인된 기존 기사 UUID인 `driver_id`. 이름/전화번호가 같다는 이유로 자동 연결하지 않는다. 연결표를 승인받고 원래 기사 행·자료 연결 건수가 유지되는지 확인한다. `require_mfa=true`는 TOTP 등록/복구 절차를 준비한 계정에만 설정한다.
5. 개인 이메일·비밀번호 로그인, 잘못된 비밀번호, 9번째 이메일 시도 제한, MFA, 갱신, 로그아웃, 복사한 이전 토큰 재사용 차단을 확인한다. 서로 다른 두 기사로 상대 일정·프로필·자료 접근을 시도하고 HQ 전용 경로가 차단되는지 확인한다. anon/authenticated의 직접 `drivers` 조회도 거부되어야 한다.
6. 기존 16건 일정의 실제 종료 일시와 기사 UUID를 관리자가 확인한다. 알 수 없는 종료는 홀드로 유지한다. 임의 18:00 입력, 동명이인 자동 병합, 실데이터 삭제로 테스트를 통과시키지 않는다.
7. HQ 두 세션에서 동시 배차, 다차량 중 마지막 행 실패, 응답 유실 후 재시도, 새로고침 후 재확인, 내용 변경 충돌을 확인한다. 저장 1건만 생성되고 기존 기록이 유지되어야 한다. 프로필 저장 실패 시 모달이 닫히거나 성공으로 표시되어서는 안 된다.
8. 실제 모바일 브라우저에서 로그인/프로필/확정/재시도/기사 확인을 검수한다. HTTP fixture 및 CI Postgres는 실제 Supabase·기기·지도·메일 제공자 검수를 대신하지 않는다. 이메일 접수의 전체 다차량·종료시간 UI와 실제 알림 전달 보장은 별도 미완료 항목이다.
9. 위 결과와 적용 SQL 목록을 소유자가 승인한 뒤 유지보수 시간에 해당 SQL만 적용하고, 서버 env와 개인 계정 연결을 준비한 릴리스를 배포한다. 새 로그인 기능만 먼저 배포해 기존 기사들을 잠그지 않는다. 실제 고객 발송은 별도 승인과 검수 후 수행한다.

## 중단·복구 기준

- 인증 함수/권한/기사 연결 또는 원자적 저장 검증 하나라도 실패하면 배포를 중단한다. DB 오류를 허용 로그인·메모리 저장으로 우회하지 않는다.
- 운영 문제 시 쓰기를 일시 중단하고 준비한 안정 버전/복구 지점으로 전환한다. 새 테이블·기사 UUID·자료를 즉시 삭제하는 파괴적 down SQL은 제공하지 않는다. 적용 전 기록한 grant/스키마와 백업으로 복구 방법을 검토한다.
- 공용 PIN을 재활성화하거나 익명 읽기를 열어 복구하지 않는다. 문제가 있는 계정은 `disabled=true` 및 공급자 세션 종료로 차단하고 매핑을 재검증한다. 비밀번호나 서비스 키를 PR/로그에 남기지 않는다.

## 증거 범위

단위 테스트는 개인 권한·프로필·HTTP 키/본문 고정·클라이언트 세션 경합을 검증한다. production HTTP smoke는 localhost Auth/PostgREST fixture를 사용하며 실제 외부 서비스에 접속하지 않는다. Postgres 16 CI는 실제 SQL 트랜잭션·권한·세션/시도 제한·기사 UUID 유지 및 연결 자료 fixture 보존을 확인한다. 운영 계정 준비와 실제 브라우저 검수는 아직 수행하지 않았다.
