# P0-02 — Tenant authentication candidate (not connected to runtime)

Parent PR #133 passed all four CI jobs, including the expanded-schema existing-data preservation job (run 45741601662). P0-00 backup/restore and live ownership evidence remain open; P0-01 SQL is still a proposal, not a deployed migration.

This PR adds an isolated server candidate and fixture tests only. Existing auth/session routes, cookies, login portal, public report/device route, current DB schema and app routing are unchanged. New candidate is hard-disabled in application code and the proposed DB remains activation-locked. No new public API or login UI. No real accounts, session tokens, personal data, or production services used in tests.

Decision chain: trusted canonical hostname (ingress adapter not implemented) -> verified domain -> active runtime-enabled organization -> provider getUser -> confirmed email, non-anonymous authenticated JWT and MFA -> existing active-session RPC -> current membership keyed by both user and organization -> tenant-owned active driver proof -> candidate identity and role-specific destination. Never infer tenant from names, query/body org, forwarded headers or editable user_metadata. No fallback from an unknown tenant to legacy VIP. Provider app_metadata may restrict access but does not grant membership. Every evaluation rereads membership; no cached authorization. Errors fail closed.

Driver ownership is intentionally denied by the actual candidate adapter until P0-03 provides a proven ownership relation (legacy drivers has no verified org column). Positive multi-membership tests use synthetic proof only. Existing rdev_ and dev signed tokens never enter the tenant evaluator. Existing VIP legacy path is not replaced. Roles are per tenant; super_admin is not a company membership role. Authentication does not by itself authorize any existing API. Before integration: secure ingress host provenance and domain verification; session cookie and refresh/logout separation; atomic membership/tenant rechecks on writes; verified driver identity linking; scoped APIs/RLS/storage; approval/invite flow, rate limits, and old-client compatibility. Revalidate verified factors and all actual Supabase Auth behavior in an isolated environment. Never enable runtime or apply live schema before backup/restore and P0 security gates pass.

Tests cover same account across two organizations with independent driver IDs/roles, malformed/unknown hosts, unverified domains, dormant organizations, provider rejection/expired/forged claims, MFA, session and membership revocation, mismatched org/user/driver, DB failures, adapter interlock, and existing routing. Existing regression CI remains intact.
