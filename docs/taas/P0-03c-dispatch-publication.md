# P0-03c — Confirmed dispatch and external fleet (review only)

Parent #136 all four CI jobs green (45755056994); both repository heads rechecked. This proposal reuses the common schedules, vehicles, dispatch_requests, existing time helpers and custody records. External and temporary supplier vehicles reference an existing verified physical UUID; supplier and vehicle composite FKs prohibit cross-tenant links. Temporary supply requires a real availability interval including turnaround. Unidentified/free-text supplier vehicles remain drafts until a verified physical vehicle is registered; no fake plates. No migration to live data.

The new readiness function checks verified route points, explicit interval, 60-minute turnaround, exact driver/vehicle/customer scope, vehicle maintenance, driver's active status/language/leave, supplier availability, custody and physical collisions. It returns generic conflict errors and never another tenant's trip details. The publish RPC rechecks membership and session, uses the existing transaction lock, checks draft revisions, records per-org idempotency and publishes the entire batch or none. It changes only candidate drafts. The existing guard function body and VIP RPC are retained. The proposal changes the guard trigger condition solely to route marked non-VIP candidates to the additional guard; all legacy/VIP rows retain the original guard. Existing custody guard stays intact. Candidate org identity and marker are immutable. Test-only activation is rolled back.

Limitations and gates: This is not a deployed availability UI or a completed operational flow. Runtime/approval holds remain. No real API imports the RPC. Full schedule version/acknowledgment/published timestamps/notification semantics, shared driver physical identity across company profiles, supplier registration UI, ownership reconciliation, tenant-scoped legacy CRUD/RLS/storage and custody writes for non-VIP are still required. The temporary supplier link represents current availability, not historical billing or provider contracts. Existing global plate uniqueness is preserved. Do not activate until all paths enforce tenant scope, backups/restore and old/new DB compatibility are verified. CI uses a synthetic DB, not a production clone.
