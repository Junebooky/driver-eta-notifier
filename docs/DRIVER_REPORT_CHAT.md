# 기사 운행보고 대화방 · 서버 Excel 누적

> 최신 PR #46 보완: [활성 장부 연도·심야 운영 설정·용량/백업 및 실기기 검수](qa/driver-report-chat/PR46_FOLLOWUP.md). 연도 없는 정상 보고는 활성 장부 연도로 자동 처리합니다. 아래 초기 구현 기록보다 이 보완 사항이 우선합니다.

기준: PR #45 통합 브랜치 `8b80650`. 전용 브랜치: `feat/driver-report-chat`.

## 화면과 사용 흐름

- `/driver/reports`: 기사 개인 로그인 후 **VIP리무진코리아**와 대화하는 화면. 한국 시간 오늘 날짜, 좌우 말풍선, 고정 메시지 입력창, 전송/재전송, 양식 불러오기, 이전 대화 조회. Enter는 줄바꿈, Ctrl/Command+Enter는 전송. 서버에 접수된 대화는 새로 접속해도 복원됩니다. 기존 운행일지 화면에는 채팅방 진입 링크만 추가했습니다.
- `/hq?tab=excel_import`: 기존 수동 가져오기 도구 위에 회사 원본 등록·자동 누적 현황·기사/상태 필터·이전 보고·대화/수정 이력·확인/재처리·다운로드·버전 복구 도구를 추가했습니다. 기존 HQ 다른 화면은 변경하지 않았습니다.
- 기사 원문과 접수 응답을 DB 트랜잭션으로 저장한 **후** Excel을 처리합니다. Excel 실패는 제출 실패로 반환하지 않습니다. 기사에게는 접수·확인 대기·실제 반영 완료를 구분해 안내합니다. 동일 전송 번호 재시도와 동일 원문 재전송은 기존 제출을 반환합니다.

## 데이터·안전 설계

마이그레이션 초안: `supabase/migrations/20261104030000_driver_report_chat.sql`. **운영 DB에 적용하지 않았습니다.**

- `report_submissions`: 조직/기사 UUID, 원문, 전송 키/중복 지문, 파싱 JSON, generated 구조화 필드(날짜·번호판·차량 UUID/표준 차종·거래처·기사·시각·경로·총근무/OT/심야 분), 반영/검토 상태, 시트/행, revision, 반영 버전.
- `report_messages`: 기사/시스템/HQ 발신 유형, 연결 제출 UUID, 영속 대화, 안정적인 순서 번호. 기사는 서버 세션의 기사 UUID와 조직으로만 조회하며 클라이언트가 보낸 다른 기사/조직 식별자는 신뢰하지 않습니다.
- `report_workbooks`, `report_workbook_versions`: 원본과 모든 성공 작업본을 bytea로 보관. 원본은 불변이며 원본/버전/최신 파일은 HQ만 다운로드합니다. 파일 크기는 12MB 이하, ZIP 확장 제한은 기존 PR #45와 동일합니다.
- Excel 쓰기는 현재 버전 UUID에 대한 compare-and-swap과 조직별 PostgreSQL 잠금으로 직렬화합니다. 경쟁 요청은 최신 파일을 읽어 다시 추가합니다. 작업본 바이트·활성 버전·제출 완료 상태·완료 답장은 하나의 DB 트랜잭션으로 커밋됩니다. 실패 시 기존 성공 버전과 제출 데이터가 남습니다.
- 버전마다 포함된 제출 UUID→시트/행 manifest를 저장합니다. 복구 시 누락된 제출을 재반영 대기로 돌리므로 이전 복구본을 다시 복구해도 상태가 어긋나지 않습니다. 복구/원본 등록 후 최대 20건을 처리하며 남은 대기/오류는 HQ 재처리 버튼으로 이어갑니다.
- HQ 검수는 revision 충돌 검사와 before/after/담당자 감사 이력을 남깁니다. 원문은 덮어쓰지 않습니다. 이미 반영된 보고를 이 경로에서 다시 수정/중복 반영하지 않습니다.
- 테이블은 RLS를 켜고 anon/authenticated 직접 접근 및 RPC 실행을 금지했습니다. 서비스 역할의 서버 API만 접근합니다. 모든 API는 개인 세션 검증, 조직 격리, 비공개 캐시, 업로드/메시지 크기 제한을 적용합니다. 변경 요청은 Origin과 실제 Host를 검사하며 임의 forwarded-host는 신뢰하지 않습니다.

## 파싱 규칙

- 차량 마스터 `VIP_REAL_VEHICLES` 재사용. 전체 번호판 일치가 우선이며 마지막 네 자리는 마스터 내 **유일할 때만** 사용합니다. 차량 UUID를 저장하고 표준 차종으로 출력합니다: `700호1458 → 스프린터 319`, `711하1058 → 스프린터 519`, `193호5336 → 카니발 하이리무진`, `125호7665 → 스타리아`. 임의 별칭/복수 번호판은 추정하지 않습니다.
- 시작·종료가 명시된 24시간 이하 근무만 계산합니다. 역전 시각을 임의로 익일로 바꾸지 않습니다. 익일은 `24:20`처럼 명시해야 합니다. 장부 연도 불명확, 기간/복수 차량, 기사명 불일치, 총시간 충돌은 회사 확인 대상입니다.
- 기본 10시간 이후의 **주간 구간**만 일반 OT, 심야는 한국 근무 관행인 **22:00~다음 날 06:00** 구간으로 분리합니다. 한 분이 OT와 심야에 중복 집계되지 않습니다. `06:00~16:40 → OT 40분`, `10:00~24:00 → OT 2시간 / 심야 2시간`. 계약 금액/수당을 계산하지 않습니다. 사용자가 22:00~다음 날 06:00 유지로 확인했습니다.
- 운행일지의 모든 화살표/줄바꿈 경유지를 원문 순서로 유지합니다. 반복 장소를 지우지 않고 시각·업무종료·특이사항·경비 구역을 제외합니다. 경유 시각 역전은 경고로 남기며 장소를 재정렬하지 않습니다.
- 기존 PR #45의 OOXML 보존 writer를 그대로 재사용합니다. A~L만 쓰며 I에 OT/심야 문구를 기록합니다. 고객 청구 금액 J/L과 결제 K는 추정하지 않습니다. 기존 파일의 X열 등 잔여 내용도 변경하지 않습니다.

## 검증 기록

- 신규 파서/API 회귀 테스트 5개 통과. 기존 Excel 회귀 8개 유지. 변경한 신규 파일 ESLint 통과.
- 실제 PostgreSQL 16 임시 DB에서 마이그레이션 반복 적용, 원문/대화 보존, 전송 키/내용 중복, 5개 독립 연결의 동시 반영 및 CAS 재시도, 불변 원본, 복구 manifest, 파일 저장 실패 롤백, 브라우저 역할 접근 금지 통과. 기존 `npm run test:db`에도 연결했습니다.
- 실제 Next.js 개발 서버 + 로컬 Supabase REST 호환 PostgREST + PostgreSQL: 회사 파일 **복제본** 등록 → 기사 채팅 전송 → 자동 OT/심야 응답 → 4월 Excel 반영 → 새로고침 대화 복원 → 동일 원문 재전송 차단 → 타 기사/Excel 접근 403 통과. 개발용 격리 세션을 사용했고 운영 인증키/DB는 쓰지 않았습니다.
- HQ 실제 컴포넌트 + 같은 로컬 백엔드: 불명확 차량 보고 확인 → 전체 번호판 수정 → 승인 → Excel 반영 → HQ 응답과 감사 이력 저장 통과. 이 검수는 전체 HQ 대시보드 E2E와 구분합니다.
- 실제 회사 파일 서버 자동 누적 출력물을 원본과 독립 ZIP/XML 비교했습니다. 원본 사용 범위 `4월!A1:X468` 뒤의 A~G/I469만 추가됐고, 기존 모든 XML 내용/셀 값/수식/서식/다른 내부 문서는 보존됐습니다. 원본과 사적 출력물은 커밋하지 않았습니다.
- 스크린샷: `docs/qa/driver-report-chat/mobile-empty.png`, `mobile-history.png`, `desktop-history.png`, `hq-inbox.png`. 모든 표시 데이터는 가상 QA 내용이며 개발 도구 배지는 캡처에서 숨겼습니다.
- 최종 코드 `38194b7`의 [GitHub CI 41765331762](https://github.com/Junebooky/driver-eta-notifier/actions/runs/41765331762): **52/52 테스트 파일, TypeScript, 프로덕션 빌드, HTTP Smoke, 의존성 감사, PostgreSQL 동시성/권한 검증 모두 통과**.

## 운영 전 준비 및 범위

1. 마이그레이션 검토·테스트 환경 적용 후 정식 배포 절차로 적용해야 합니다. 기존 Supabase URL/service-role 바인딩을 사용하며 별도 운영 DB를 직접 변경하지 않았습니다.
2. HQ에서 **승인된 월별 시트가 들어 있는 회사 Excel**을 최초 등록해야 합니다. 업로드 파일에 월 시트가 없으면 양식을 임의로 만들지 않고 제출을 보관한 채 HQ 재처리 대상으로 남깁니다. 실제 제공 파일에는 4월만 있으므로 10월 시나리오는 승인된 10월 시트를 준비한 뒤 가능합니다. 등록 후 원본을 임의 교체하는 기능은 없습니다.
3. 파일 저장소는 이번 버전에서는 PostgreSQL bytea입니다. 보고당 불변 파일 버전을 보관하므로 DB 용량, 백업/보존 기간, 배포 플랫폼의 요청/응답 크기 제한을 점검해야 합니다. 대규모 운영은 private object storage로 분리하는 후속 설계가 필요합니다.
4. 영수증·경비 상세·Microsoft Graph·OneDrive 자동 쓰기·실제 카카오톡 계정 연동/발송은 추가하지 않았습니다. 이 화면은 회사 전용 웹 대화방입니다.
5. iOS Safari 실제 키보드/재접속, 장기간 대화·대량 파일, Excel 데스크톱 표시/인쇄/정산 합계, 월 템플릿은 회사 확인이 필요합니다. 심야 기준은 사용자 확인을 받았습니다. 기존 수식 범위를 자동 확장하거나 청구액을 만들지 않습니다.
6. main 병합·운영 DB 변경·배포는 수행하지 않았습니다.
