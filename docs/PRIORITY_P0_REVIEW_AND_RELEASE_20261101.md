# P0: 영수증 검수·고객 안내 기록의 정확성 및 운영 사전 점검

기존 통합 PR #40을 확장했다. 별도 영수증 화면·메일 엔진·배차 저장소를 만들지 않는다. main 병합, 운영 스키마 변경, 실제 고객 메시지 발송은 이 작업에 포함하지 않았다.

## 수정한 업무 흐름

### 영수증 검수와 청구 구분

- 서버 PUT이 실패하면 로컬 승인으로 대체하던 경로를 제거했다. 성공 토스트·성공 진동은 서버에서 해당 ID와 요청 상태/청구 구분, 저장 버전을 확인한 뒤에만 표시한다.
- 고객사 청구 / 회사 부담 직접비 버튼도 기존 PUT API에 저장한다. 이전에는 브라우저 캐시만 바꿔서 다른 PC와 기사 화면에 반영되지 않았다.
- 서버가 반환한 실제 검수자·검수 이력·새 버전으로 캐시를 갱신한다. 서버에 없는 로컬 예시 영수증은 승인할 수 없다.
- 저장 중 세 버튼과 청구 구분을 잠그고 같은 프레임의 중복 클릭도 ref로 차단한다. 실패 시 상태·검수 의견을 보존한다. 의견 초안은 작성 시작 버전을 유지해 20초 조회가 초안을 최신 버전인 것처럼 덮어쓰지 않게 한다.
- PUT은 조직 소유권 확인, 입력 상태/메모 검증, 선택적 클라이언트 버전 검사, 읽은 `updated_at`에 대한 조건부 갱신을 수행한다. 오래된 검수는 409로 거절하고 감사 이력을 보존한다. 구버전 호출도 서버 조회 이후 경합은 조건부 갱신으로 막는다.
- 회전은 미리보기에만 적용한다. 서버 원본을 브라우저에서 재인코딩하거나 로컬 영수증 URL로 바꿔 원본과 다르게 만들지 않는다.

### 기사·차량 Info 자료 기록

- 기존 수동 자료 기록 엔드포인트가 이메일 선택만으로 ‘발송됨’을 표시하던 문제를 수정했다. 이 엔드포인트는 이메일/문자 발송을 수행하지 않는다.
- 기본은 `준비완료` / snapshot `prepared`다. 실제 수신처와 ‘직접 전달했다’는 명시적 확인을 받은 경우에만 `수동 발송 기록` / `manual_recorded`, `operator_attested` 증거를 남긴다. SMTP 접수·고객 수신/열람과 구별한다.
- 예약을 서버에서 조회해 조직, 확정 배차 여부, 기사 UUID, 차량 UUID·정확한 번호판, 배차 버전을 검증한다. 취소·미확정·다른 차량·다른 조직·오래된 배차 요청은 기록 전에 차단한다. GET 불일치 판정도 요청 쿼리의 기사/차량을 신뢰하지 않고 서버 예약을 사용한다.
- 일정 조회기가 실제로 읽는 `customerBrochure` 필드에 저장한다. 기존 코드의 snake_case 저장/ camelCase 조회 불일치를 수정하고 기존 encoded 메타데이터도 함께 보존한다.
- 로컬 ‘완료 표시’ 우회 버튼과 콜백의 무조건 ‘발송됨’ 지정은 제거했다. 부모 화면은 서버에서 일정 반영까지 확인한 경우에만 해당 상태를 적용한다.
- 불변 로그 저장 후 일정 조건부 갱신은 별도 작업이다. 로그가 보존됐지만 일정 갱신 실패/경합이 발생하면 `scheduleSynced:false`와 경고를 반환한다. 재발송을 유도하지 않고 최신 기록 확인을 안내한다. 이를 단일 트랜잭션으로 보장한다고 주장하지 않는다.
- 자료 조회 중 이전 예약 자료를 보여주지 않으며, 늦게 도착한 요청 응답이 새 예약 자료를 덮어쓰지 못하게 한다. 배차 변경 시 수신처/수동 확인을 새로 초기화한다.
- 과거 `sent` 이력은 실제 발송 증거를 사후에 추정해 바꾸지 않았다. UI에서는 ‘이전 발송 기록’으로 표시한다. 실제 SMTP Info 전달은 기존 NAVER 서비스에 연결할 후속 작업이다.

## 운영 준비를 재현 가능하게 점검

`supabase/checks/release_preflight.sql`을 운영 프로젝트에서 읽기 전용 트랜잭션으로 실행했다. SQL은 스키마·권한과 집계만 조회하며 계정 이메일/UUID·기사 이름·예약 내용을 반환하지 않는다.

2026-11-01 조회 결과:

| 항목 | 결과 / 후속 조치 |
| --- | --- |
| 대표 계정 | 서버 관리 대표 권한 1개 연결 유지 |
| 기사 계정 | 0개, 확인된 실제 개인 계정과 기존 UUID 연결 필요 |
| 기사 테이블 | 34행; 34명의 실제 기사라고 간주하거나 자동 병합하지 않음 |
| 기존 예약 | 16건, 모두 기사 UUID·종료 일시 확인 필요 |
| 신규 테이블 | 차량 마스터·차량 상태·원자적 요청·인증·보고·Info 테이블 10개 미설치 |
| 필수 RPC | 원자적 배차·인증 시도 제한·실세션 검사·프로필 수정·보고 집계 5개 미설치 |
| 메일 날짜/차량 슬롯 고유 인덱스 | 미설치 |
| 원본 자료 bucket | `cockpit-assets`, 비공개 유지 |
| drivers 직접 접근 | RLS 켜짐, authenticated 테이블 권한 존재. 기존 클라이언트 의존성과 정책을 확인하고 개인 인증 릴리스와 함께 권한 제안 적용 |

이 SQL의 테이블 권한 표시는 권한 존재를 보여준다. RLS 정책에 따른 특정 사용자의 실제 행 접근 허용을 증명하지 않는다. 정상 반환은 배포 승인이나 ‘운영 준비 완료’가 아니며 누락·매핑·실제 공급자/기기 검수 결과를 함께 판단해야 한다.

개인 인증·원자적 배차·보고 제안은 격리 Postgres에서 검증한다. 운영에는 기존 `PERSONAL_AUTH_RELEASE_PLAN.md` 순서에 따라 실제 스키마 차이·복구 지점·매핑을 확인한 SQL만 적용해야 한다. 오래된 asset 제안은 정책 생성의 재실행 안전성·현재 권한 설계를 별도로 검토해야 한다. 전체 migrations 폴더를 일괄 재생하지 않는다. 종료 시각·실제 기사 계정은 추정으로 채우지 않는다.

## 검증 범위

- 전체 42개 테스트 파일, TypeScript, 프로덕션 빌드.
- 새 회귀 검사: 503/응답 유실/잘못된 성공 본문에서 로컬 승인·청구 구분 보존, 서버 검수자·이력 채택; Info의 수동 확인·확정 배차 연결·타 조직/구버전/위조 번호판 차단·일정 mapper 연결·부분 실패/경합 경고.
- 기존 실 Postgres 보고 통합 흐름에 실제 클라이언트 검수 함수 → PUT → DB → 기사 재조회, 오래된 검수 409/감사 이력 유지와 청구 구분 저장 검사를 추가했다.
- Chromium 390/1280px에서 실제 비밀번호 로그인→실패한 검수의 대기 상태 유지→중복 요청 잠금→서버 검수자 반영→청구 구분 실패/성공→회전 후 원본 URL 유지→다른 기기 변경을 재조회한 뒤 오래된 의견 저장 거절/초안 보존을 확인했다. 프로덕션 HTTP smoke도 통과했다. 최종 CI 결과는 PR 설명에 기록한다. Auth/보고/이미지는 격리 fixture이며 실제 Supabase 계정·실물 OCR·고객 발송·실제 설치형 PWA 검수를 대신하지 않는다.

## 다음 우선순위

먼저 운영 스키마와 확인된 기사 매핑을 준비하고 실제 업무 1건을 접수→배차→기사 확인→운행일지/경비→HQ 검수까지 검증한다. 그 후 기존 인수·반납 UI의 서버 연결, 영수증 필드 교정/좌우 검수·승인 후 다음 이동과 실물 OCR 검수, 푸시 전달 채널, 고객 Info 실제 전달, 차량/현장 팁 공통 저장을 진행한다. 이미 구현된 UI/API를 확장한다.
